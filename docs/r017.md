# R017-budget-fit: the independently reproduced Budget-Fit single agent, adapted (pre-registered; results below)

**Hypothesis (one):** replicating the independently reproduced Budget-Fit single-agent recipe (hard 28-call budget,
8-min task timeout, thinking on with thoughts kept, concise contract-first prompt) reduces unproductive exploration and
increases correctly resolved tasks.

**Controls:**
- R016 (9/24, the primary paired control);
- R015 (10/24).

Both ran on the same harness, task set and notebook.

## 1. Harness verification (2026-10-12, before implementation)
- **Wheelhouse** `metric/gemma-4-developer-agent-wheelhouse`: last updated 2026-10-09 14:43, unchanged since R015/R016.
  Versions: adk-submission 0.2.13, swegemma 0.2.11, adk_eval_core 0.1.0, google-adk 1.36.1, vLLM 0.19.1; same sizes as our
  local copies.
- **Thinking resolution** (adk_submission/resolvers/generation.py `apply_thinking_config_to_model`):
  - a positive `thinking_budget` → `enable_thinking: true`, forwarded as `thinking_token_budget`;
  - `include_thoughts: false` strips thought parts from history; `true` keeps them (LiteLLM reasoning patch: mirrors
    `reasoning_content` into `reasoning` on outgoing assistant messages);
  - the harness default `thinking_budget: 4096` is merged into every agent's config.
- **Focused retention test** (`scripts/thought_retention_check.py`, official venv): it compiles a submission with the official
  `compile_submission`, serves a scripted turn with `reasoning_content` = a unique marker plus a tool call, and inspects the
  next request.

| archive | turn-1 request | turn-2 assistant message carries the marker | verdict |
|---|---|---|---|
| R016 (`include_thoughts: true`) | `enable_thinking: true`, `thinking_token_budget: 4096` | yes (`reasoning`, `reasoning_content`) | **RETAINED** |

- **Call cap enforcement** (swegemma 0.2.11):
  - every harness tool is `budget_gated` (`context.check_budget` increments the count; past the cap it returns
    `BudgetExceeded`);
  - skill scripts go through `AdkSandboxCodeExecutor(budget_check_fn=context.check_budget)`, so they count too;
  - `agent_runner` ends the loop when `tool_calls_used >= budget.tool_calls` ("Agent exceeded tool call budget").
  - So `max_tool_calls: 28` is a hard, enforced cap, not a prompt request. The same code also enforces
    `max_time_minutes` and `max_turns`.

## 4. Runtime protection
- The theoretical worst case is 120 × (8 + 0.5) min + 15 min ≈ 17.3 h, which would error the whole submission.
- Whether R017 fits depends on how often the 28-call cap ends tasks before 8 min.
- The projection must come from measurement: agent-phase wall time per task (including sandbox and grading, from the
  kernel log) × 120 tasks + 15 min server start.

## 5. Pre-registered gate (recorded before the R017 run)
Controls: R016 = 9/24 (no edit 12, wrong fix 3, time caps 14); R015 = 10/24. Same tasks, order, harness and notebook.

**R017 passes only if all of:**
1. **≥ 14/24 resolved.**
2. **wins − losses ≥ 3 vs R016** (paired, per task).
3. **No material regression vs R015:** resolved ≥ 10 and paired losses vs R015 ≤ 2.
4. **Fewer no-edit / time-exhaustion failures than R016:** no-edit < 12 **and** time-cap hits < 14.
5. **No unhandled tool-contract or architecture failures:** 0 harness/sandbox errors.
6. **No substantial increase in incorrect patches or regressions:** wrong fix (edited, unresolved) ≤ R016's 3 + 2.
7. **Runtime margin:** projected full run (section 4) ≤ 10.5 h (≥ 1.5 h under the 12 h limit).

A faster agent that does not resolve more tasks is not a success. If R017 fails, it is analysed and work stops (no R018).

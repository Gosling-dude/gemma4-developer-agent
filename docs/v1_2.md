## 5. Budget (worst case = every task hits the cap; 15 min server start, 0.15 min setup/task, both over-estimates)
| cap | 116 tasks | 120 tasks | verdict |
|---|---|---|---|
| 4.0 min | 8.3 h | 8.6 h | safe |
| 4.5 min | 9.2 h | 9.6 h | safe |
| 5.0 min (V1.1) | 10.2 h | 10.6 h | safe |
| **5.5 min (V1.2)** | **11.2 h** | **11.6 h** | safe (≥ 27 min margin) |
| 6.0 min | 12.1 h | 12.6 h | **fails**: validator error |

Calls: at 3.5–5.6 s per call (3P), 60 calls last 3.5–5.6 min and 80 calls 4.7–7.5 min, so at 80 the time cap is
usually the one that binds. Tool and turn caps don't affect the 12 h guarantee; only `max_time_minutes` does.
A 4.0/4.5 run is not planned: the only public A/B (4 min vs uncapped) points the other way.

Same tasks, same vLLM session, one variable per comparison:

| Variant | = | Question |
|---|---|---|

```bash
scripts/run_kaggle_eval.sh --exp-id R002-v12-matrix-a --variants v1_1 root v11_budget v12_v11budget --n-tasks 12
scripts/run_kaggle_eval.sh --exp-id R003-v12-matrix-b --variants root v12_analyzer v12_reviewer v12_both --n-tasks 12
python -m g4agent.real_report evaluations/results/R002-v12-matrix-a --tasks <competition tasks.jsonl>
```
Worst case 4 variants × 12 tasks × 5.5 min ≈ 4.4 h per notebook. `real_report` gives per variant: resolved, runtime,
calls, first-edit call, `edit_file` failures, code-edit use, cap types, discarded patches, edit locations, and
task-by-task pairs. With ~12 dev tasks per variant, only large effects (≥ 3 tasks) are distinguishable from noise
(3P: run-to-run s.d. ≈ 2.4 tasks per 106).

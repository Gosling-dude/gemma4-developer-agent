# R012-v13-handoff: read-only localization handoff before the V1.3 coder (Phase 2: FAIL)

**Hypothesis (one):** a forced, read-only localization stage whose short plan seeds the coder lowers wrong-file /
wrong-fix failures (class B = 19 of 38 valid real-Gemma failures, R004–R011) and so raises resolution. R010 showed
a prompt-only diagnosis rule is ignored (0/12 compliance); here the stage is structural.

**Base:** commit `121bd79` = the R009 build; packaging it reproduces archive `1e344ea7…` byte for byte (staged as
`submission/r012-v13-base/submission.zip`). R010's diagnosis rule is not included.

Harness facts that shaped it (official swegemma 0.2.7 / google-adk 1.36.1 source):
- An undeclared tool call raises `ValueError` (no callback catches it) and ends the task, so the localizer keeps
  every tool the harness prompt names (graph tools) and gets no write tools; its prompt names none of the absent ones.
- `include_contents: none` starts the coder at the localizer's final reply: the coder does not carry the localizer's
  tool output or the harness's first message (budget lines, environment rules, workspace tree); the issue reaches it
  through `{problem_description}`.
- A harness nudge (turn ended without `submit_patch`) re-runs the whole sequence (a sub-agent of a SequentialAgent
  is not resumable). The localizer then repeats its plan (1 LLM call, no tools), but the coder restarts without its
  earlier history (its edits stay in the tree). Nudges: 0 of 30 tasks in R008–R010.

### Localizer budget compliance (separate metric; time/budget risk)
The localizer prompt asks for ≤ ~12 calls; nothing enforces it.
- ≤ 12 calls: **13/24** (includes the 2 crashed tasks at 9 and 3 calls) · > 12 calls: **11/24** · max **79** (rich_3052)
- over budget: rich_3052 79, rich_3067 46, fastapi_11194 34, rich_3063 18, rich_3470 18, requests_6644 18,
  rich_3480 17, rich_2943 16, rich_3180 16, rich_3468 16, rich_3471 14
- localizer wall time: mean 46.5 s, median 32 s, 22.6 % of all task time (non-crashed tasks)
- did excess localization reduce coder time materially? **On one task decisively, not systematically.**
  - rich_3052: 79 calls, 242 s spent repeating a malformed `read_file` (`end_line"` key), which left the coder 89 s → time cap, no patch.
  - rich_3067: 46 calls / 113 s, ending in a wrong-file plan (`rich/markup.py`; gold is `rich/highlighter.py`).
  - fastapi_11194: 34 calls / 93 s, still resolved, with 65 s of coder time.
  - rich_3468: 16 calls / 35 s; the coder still had 300 s and timed out while editing. The excess was not decisive here.
  - Over-budget tasks resolved 2/11 vs 9/11 at ≤ 12 calls, but the baseline also resolved only 2/11 of the
    over-budget set: long localization marks hard tasks more than it causes failures. Mean coder time was similar
    (174 s vs 166 s).
  - Risk: with a 5.5-min cap, an unbounded localizer can consume the whole budget (rich_3052), and on the
    hidden set this is an unmeasured tail risk.

### Failure modes
- **Dominant: wrong fix on the right file (class B, 8 of 13 candidate failures).** In 7 of the 8 the plan named the gold
  file (rich_3067 is the wrong-file exception). The handoff converts no-patch failures into wrong patches (D 10 → 2,
  B 4 → 8): localization is no longer the bottleneck; producing the correct repair is.
- Harness crash from the localizer calling an undeclared tool (2): defect above, still present in this build.
- Unbounded localizer (see budget section), including the rich_3052 malformed-argument loop (class C).
- The one loss (rich_2943) is a wrong fix on the gold file after 16 localizer calls; the baseline solved it in 44 s.

# R014-v13-editfirst: the coder applies a code-confirmed plan before reproducing (evaluated: 13/24, strong-success gate not met)

**Hypothesis (one):** reordering the coder workflow so it applies the trusted repair plan before attempting
reproduction reduces budget exhaustion and incorrect/no-patch outcomes, while preserving the R013 localization
and tool-guard behavior.

**Base / control:** R013-v13-toolguard, commit `1cbcbd7`, archive `ccd2cd5d…`.

Pooled over both runs, the 23 resolved tasks were never left without an edit. The 20 unresolved correct-file tasks
had 7 never edited, 10 with long identical-call runs, and existing tests run after the last edit in only 3 of 13.
The model follows the workflow's step order literally: REPRODUCE was step 3 and EDIT step 5, and the coder reproduced
first in every correct-file run. It ignores count limits: "1–2 calls" and "first edit by call 12" were already in
the prompt. Three resolved tasks used 8–16 varied repro runs before editing (fastapi_14873, fastapi_15589,
rich_2725), so a hard cap on reproduction would put them at risk. R014 changes the order instead.

## Change (coder prompt only, `prompts/system.md`)
1. **Step 3 `REPRODUCE` → `3. REPAIR FIRST (no tool call)`.** Decide from the code just read (step 2 still reads
   the plan's code with nav.py and checks its CAUSE):
   - If the code confirms the plan's CAUSE, the plan's EDIT is the hypothesis. Do step 4 (hypothesis) and step 5
     (edit) now, and reproduce only in step 6, after the edit.
   - If the plan is empty, unknown or contradicted by the code, locate, then at most 2 script runs to find the cause,
     then steps 4–5. (A contradicted plan is not trusted blindly.)
   - Probing never takes most of the budget before the first edit: at half the time or tool calls with no edit, make
     the best-supported edit, then verify.
2. **Step 6 `VERIFY` → `6. VERIFY, REPRODUCING AFTER THE EDIT`.** The repro template moved here and is run as
   `timeout 20 python3 /tmp/repro.py`. The model copies templates verbatim and never used the skill runner, so a
   hanging repro costs 20 s, not the session. Two script versions that don't show the issue's behaviour → stop
   scripting and rely on the tests. The existing-test run, classification and ≤3 repair rounds are unchanged.
3. **Step 6, rich_3470:** "Tests are evidence, not the spec." An existing test that asserts exactly the behaviour the
   issue reports as the bug is stale (the grader replaces it with the updated test). Keep a fix that matches the
   issue: don't change the code back and don't edit the test. Repair or revert only for failures in behaviour the
   issue does not ask to change.

Unchanged in the prompt: steps 1, 2, 4, 5 (edit mechanics, byte-identical, so no splicing path is added for
rich_3052), 7, 8, the operating rules, budget discipline and quality bar. The exact old/new text is pinned in
`tests/test_r014_edit_first.py::R014_CHANGES`; undoing it restores the R013 prompt (`78e65655…`) byte for byte.

`timeout` is coreutils, the same package as the `cat`/`ls`/`sed` the coder uses in every Kaggle trace. No trace
used it yet, so its presence in the sandbox is inferred, not observed. If it were missing, the result is a cheap
"command not found", not a hang.

## Expected effects
- Correct-file-plan tasks: edit-before-repro rises from 0 % toward most tasks. The first edit comes earlier. Never-edited and
  repro-loop time caps fall.
- Target tasks are R013's six repro-loop failures: rich_3480, rich_3454, rich_3063, rich_3061 (the plan was right and
  the fix never landed or landed too late), plus rich_3180 and rich_3278 (identical-call loops). rich_3470 is covered by
  the stale-test rule.
- Risk: an early edit from a plausible but wrong plan. It is mitigated by step 6 verification and the unchanged ≤3 repair rounds.
  Wrong-fix-after-edit counts are watched in the gate.
- Not addressed: rich_3471 (wrong root cause), rich_3468 (unstated contract), the wrong-file plans (rich_3067, rich_3105) and localizer budget overruns.

losses demonstrably unrelated to the change. That exception must be argued from per-task traces. If edit-before-repro
stays below 25 %, the instruction was not followed and any score change is variance.

### What the traces show
- **The literal order was not adopted.** In all 21 correct-file tasks the coder still ran a script before its first
  edit, so edit-before-repro is 0 / 21, as in R013.
- **The "at most 2 runs, half-budget" part partly took effect.** The median of runs before the edit halved, the first
  edit came in about half the time, never-edited fell from 4 to 1, and time caps fell from 8 to 3.
- **Wins (target tasks):**
  - rich_3454: 44 repros, edit at 263 s → 2 repros, edit at 21 s, resolved.
  - rich_3063: 38 repros, no edit → 25 repros, edit at 142 s, resolved.
  - rich_3470: a gold-equivalent patch that was not reverted. The traces show no stale-test reasoning, so this win is
    not attributed to the stale-test rule.
- **Losses:**
  - fastapi_15589: about 28 repro scripts; it wrote `/tmp/new.txt` but never applied it; timed out. This is the
    targeted failure with the instruction ignored; R013 happened to edit at call 18.
  - fastapi_5077: about 10 repros, then an edit at 174 s with a plausible but wrong fix (`__wrapped__` globals; the
    hidden test still fails on a ForwardRef).
  Neither loss shows a behaviour the change introduced.
- **Edits that landed but were wrong (no-patch → wrong-patch, the R012 pattern again):**
  - rich_3480: the plan's fix now lands at 24 s (R013: never), but it misses the twin `append_text`.
  - rich_3061: 6 edits; it broke existing tab tests and timed out.
  - rich_3052: no SyntaxError this time, but the logic is incomplete (it returns the raw input instead of the
    matching choice).
  - rich_3278, rich_3180, rich_3468, rich_3471: wrong fixes as in R013. rich_3278 again submitted with no test run.

**Verdict: modest / inconclusive, not a strong success.** By the pre-registered rule, the +1 cannot be attributed to the
change: the ordering instruction itself was not followed, and +1 (3 wins, 2 losses) is within the ±2 run-to-run range.
The budget-exhaustion mechanism did move in the intended direction: fewer never-edited tasks, earlier first edits,
fewer time caps, and two target tasks resolved with sharply shorter repro loops. Those gains were offset by more
wrong fixes after an edit (6 → 8). This is not an adoption-grade improvement over R013. The R013 archive remains the
control; R014 is not recommended for submission on this evidence.

# R013-localizer-tool-guard: stop the R012 localizer from calling tools it does not have (evaluated: all checks met)

**Hypothesis (one):** preventing undeclared-tool calls improves R012 reliability without changing repair
behavior. Base: R012-v13-handoff (`07b520e`, archive `510145e0…`). Not run on Kaggle, not submitted.

## R012 failure evidence
2 of 24 R012-v13-handoff tasks ended in the localizer with `Sandbox execution error: Tool 'run_command' not found`
(google-adk 1.36.1 `ValueError`), no plan, no patch, score 0 (`evaluations/results/R012-v13-handoff/`, traces):

| Task | Localizer calls before the crash |
|---|---|
| rich_3061 | `load_skill("repo-navigation")` → `find Text.extend_tabs` (0 hits) → `find extend_tabs` (0) → `search_similar_code` (0) → `find Text` → `show Text.extend_tabs` (not found) → `read_file rich/text.py` → `find extend_tabs` (identical-call notice) → **`run_command("grep -n \"extend_tabs\" rich/text.py")`** at 15.6 s |
| rich_3105 | `load_skill("repo-navigation")` → `find #3104` (0 hits) → **`run_command("git log -n 10 --grep=\"#3104\"")`** at 5.7 s |

**Cause.** The only place the localizer's context named `run_command` was the shared `repo-navigation` skill,
which it loaded first in both tasks. Its last line says: *"If a script errors, don't retry it. Fall back to
`run_command("git grep -n -e 'term' -- '*.py' | head -40")`."*, and `references/graph_tools.md` compares graph
calls to "`run_command`". Both crashes follow an empty or repeated `find`, which is exactly that fallback's
trigger. The localizer's tool declarations, its prompt and the harness prompt do not name `run_command`.

**Why prevention, not catching.** ADK runs `on_tool_error_callbacks` for an unknown tool name, and an
`after_model_callback` could rewrite the call, but a submission cannot register either:
- `adk-submission` 0.2.11 resolves callbacks through a closed `CallbackRegistry`, and swegemma 0.2.7 registers none.
- The YAML schema has no `on_tool_error_callbacks` key, and `before_tool_callbacks` run only after tool lookup succeeds.
- Our validator's `LLM_AGENT_KEYS` already excludes callbacks (`docs/public_research.md`: "callback registry is empty").

So no run-time guard exists inside the competition format. The only lever is what the model is shown.

## Tests (`tests/test_r013_tool_guard.py`, 7 new)
- The localizer uses the read-only skill; its tools are unchanged; its `nav.py` equals the shared one, which keeps its R012 hash.
- Nothing the localizer sees names a missing tool: no skill file mentions one, and the instruction shows none in call form. The contract text and the five plan fields are present exactly once.
- The validator rejects the R012 configuration (localizer + shared skill → `SKILL.md names tool 'run_command'`) and rejects a `run_command(...)` call shown in the localizer instruction.
- The coder never triggers the guard.
- **Regression replay of rich_3105 through real google-adk with a scripted model:** `load_skill` → empty `find #3104` → the step where R012 crashed. The loaded skill text names no missing tool. The localizer hands off `FILE: unknown … CHECK: run git log …`, and the coder fixes and submits (`stop_reason == "submitted"`).
- **Characterization:** if the model calls `run_command` from the localizer anyway, ADK still raises `Tool 'run_command' not found` and the task ends (`agent_error`, no patch). This pins why the guard must be preventive.

Updated: `tests/test_handoff.py` (the localizer skill invariant) and `tests/test_runner_integration.py` (the scripted
localizer's `skill_name`). In `tests/test_packager.py`, `v1_nograph` is now a strict xfail. The new guard rejects that
V1.1 ablation because its skills name the graph tools it removes, which is the same latent crash. Variants are not
built from this branch (docs/r012.md caveat).

### Summary
- **Overall:** 12 / 24 (50.0 %) vs R012 11 / 24.
- **Per task vs R012:** 2 wins (rich_2943, fastapi_5077), 1 loss (rich_3454: gold-file edit at call 57, then a timeout), 21 ties.
  This is within the run-to-run noise seen before (same build ±2/12), so repair behavior is unchanged as intended.
- **The two R012 crash tasks:** both now produce a plan and reach the coder. Neither is resolved (never resolved by any build):
  - rich_3061: correct-file plan (`rich/text.py`); the coder timed out without a patch.
  - rich_3105: wrong-file plan (`rich/cells.py`; gold is `rich/_export_format.py`); wrong patch.
- **Failure classes, R013 vs R012:** wrong fix 8 vs 8; no patch 4 vs 2; tool-argument 0 vs 1; harness crash 0 vs 2.
  Time caps 8 vs 5. In 3 of the 8 the task was still resolved, because the fix was already in the tree.
  rich_3480's coder repro hung on the issue's own infinite loop.
- **Localizer budget:** 10 / 24 tasks still exceed 12 calls (R012: 11 / 24); max 40 (rich_3468). Not addressed by R013.
- **Hypothesis:** supported on this run. Preventing undeclared-tool calls removed the 2 harness crashes without changing
  repair behavior. Dominant remaining failure: wrong fix on the correct file (8 / 12 failures).
